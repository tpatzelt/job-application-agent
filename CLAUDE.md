# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An agentic job finder: it uses the Brave Search API to find job listings, `botasaurus` to fetch and scrape page content, and an LLM (via `litellm`, default `openrouter/openrouter/free`) in a plan → act → reflect loop with persistent cross-run memory. Results above a score threshold are written to `data/results.json` / `data/results.csv`.

It runs in two modes: a one-shot single-user CLI (`src.main`, profile from `user_profile.txt`/`preferences.json`) and an always-on **multi-user Telegram bot service** (`src.bot_service`, intended to run as a Docker service) where each user onboards by uploading a CV / motivation letter / job description, gets LLM-extracted search parameters (with follow-up questions for missing essentials like country/cities), and receives periodic per-user scans.

## Commands

```bash
uv sync                          # install dependencies
uv run python -m src.main        # one-shot CLI crawl (needs .env with BRAVE_API_KEY, OPENROUTER_API_KEY)
uv run python -m src.bot_service # always-on multi-user Telegram bot (also needs TELEGRAM_BOT_TOKEN)
uv run python -m src.dashboard   # standalone monitoring dashboard (http://127.0.0.1:8765)
docker compose up -d --build     # run the bot service in Docker (restart unless-stopped, ./data volume)
uv run python run_mock_test.py   # run the mock end-to-end loop (no network/API keys needed)
uv run pytest -q                 # run unit tests
uv run pytest tests/test_agent_loop.py::test_plan_generated_once_and_passed_to_query_context  # run a single test
uv run python -m evals.run_eval --tag <name>   # integration eval: run the real agent for 6 search profiles, score results
RUN_INTEGRATION_EVAL=1 uv run pytest tests/test_integration_eval.py -s  # same loop as an opt-in pytest (RUN_INTEGRATION_EVAL=all for all profiles)
```

Profile selection (see `pyproject.toml` `[tool.job_crawler.profiles.*]`, currently only `minimal`):

```bash
JOB_CRAWLER_PROFILE=minimal uv run python -m src.main
```

`LOG_LEVEL` env var controls log verbosity (default `INFO`). Logging is configured by `src/logging_setup.py` (used by both entrypoints): besides the console, logs go to a daily-rotating file under `data/logs/` (`crawler.log` for `src.main`, `bot.log` for `src.bot_service`), rotated at midnight UTC and kept for `LOG_RETENTION_DAYS` days (default 30); `LOG_DIR` overrides the directory. In Docker the files persist via the `./data` volume.

CI (`.github/workflows/ci.yml`) runs `pytest -q` then `python run_mock_test.py` on every push/PR to `main`. `.github/workflows/docker.yml` builds and pushes the amd64 image to `ghcr.io/tpatzelt/job-application-agent` (`:latest`, branch and `sha-*` tags) on pushes to `main`/`tp/v1` and `v*` tags; `docs/HOSTING.md` documents running that image on a server/homelab.

## Architecture

Everything is wired together in `src/main.py`, which loads config/secrets and constructs the three collaborating services passed into `Orchestrator`:

- **`config_manager.py`** — loads `Config` and `EffortBudget` from `pyproject.toml` (`[tool.job_crawler]`, merged with an optional `[tool.job_crawler.profiles.<name>]` override selected via `JOB_CRAWLER_PROFILE`). Also loads `.env` secrets (`BRAVE_API_KEY`, `OPENROUTER_API_KEY`), `user_profile.txt` (raw CV text), and `preferences.json`. `EffortBudget` is a shared mutable counter (LLM calls / search iterations) passed by reference into both `LLMService` and `CrawlerEngine` so a single run-wide cap is enforced across both. The budget's two caps come from `[tool.job_crawler.budget]` but can be overridden per-deployment via `.env` (`JOB_CRAWLER_MAX_LLM_CALLS`, `JOB_CRAWLER_MAX_SEARCH_ITERATIONS`) so operators can tune cost without editing checked-in config.
- **`llm_service.py`** (`LLMService`) — builds JSON-only prompts for five tasks (plan the search, generate search queries, evaluate a job against the CV, reflect on search performance, extract a search profile from intake documents) and calls `litellm.completion`. Since free/small models often return malformed JSON, there's a multi-layer repair pipeline: `_parse_json_payload` → `_extract_json_object` (strip markdown fences, slice between first `{`/last `}`) → `_retry_json_response` (a second LLM call asking it to fix its own output). Every retry/repair call also consumes the shared `EffortBudget`. `plan_search`/`reflect` return safe defaults on validation failure.
- **`crawler_engine.py`** (`CrawlerEngine`) — `search()` calls the Brave API (via a `botasaurus`-wrapped `@request` task with retries) with rate limiting (min 1.5s between calls, exponential backoff on 429s) and filters out video results by URL/hostname heuristics. `fetch_page()` fetches a URL and returns `(text, links)`: plain text via BeautifulSoup (`soupify`, removing script/style/nav/header/footer) plus the page's absolute, de-duplicated outbound hrefs; `fetch_job_text()` is the text-only wrapper. When called with `use_browser_fallback=True` (the orchestrator sets this for POSTING- and LISTING-classified URLs) and the plain fetch yields under `min_job_text_chars`, it retries with a headless-browser `@browser` task to handle JS-rendered ATS pages and 403-blocking boards, keeping whichever text is longer (links then come from the browser-rendered HTML); browser failures degrade back to the plain result. Gated by `browser_fallback` in `[tool.job_crawler.search]`.
- **`orchestrator.py`** (`Orchestrator.run`) — the agent loop: (1) **plan** — ask the LLM for a `SearchPlan` (roles/skills/locations/strategy; failure is non-fatal); (2) **act** — while under `max_results`/budget, generate queries (context includes the plan, memory summary, and latest reflection), skip queries already searched this run or known-ineffective from memory, search each query, triage new URLs via `url_heuristics.classify_url()` and process employer-hosted postings first, careers/listing pages next, and aggregator-hosted postings plus board index pages only if capacity remains (non-job URLs are dropped; aggregator index pages are dropped outright when `exclude_aggregator_sites` is set — Brave ignores `-site:` exclusions in queries, so filtering happens on results). Careers/board pages that link to individual postings aren't scored themselves: up to `max_harvest_links` posting-classified links are harvested from the page (employer/ATS hosts before aggregator mirrors) and each is fetched and scored instead, so results point at the actual job on the employer's site. Pages under 800 chars are skipped, as are pages carrying a closed/expired marker (`page_signals.find_stale_marker`) and pages that never mention any preferred location (`page_signals.mentions_location` — a deterministic gate because small models sometimes ignore the location prompt rule); remaining pages are scored with the LLM (`evaluate_job` receives the preferences — including `job_titles`/`job_description_keywords`/`industries` — and an evaluation with `location_match == False` or `domain_match == False` is rejected regardless of score, so a matching job title in the wrong industry, e.g. software PM vs food PM, doesn't get through), keeping results `>= min_score`. Searches are scoped to the user's country (`page_signals.country_code_for` on the preference locations → Brave `country` param) and to the preferred posting language (`preferences["language"]`, defaulting to the CV's detected language via `language.detect_language` → Brave `search_lang` param; the resolved language is also injected into `preferences` so the query/plan prompts generate queries in that language); (3) **reflect** — between iterations, ask the LLM to critique query performance (falling back to `_heuristic_reflection` on any error) and feed the result into the next iteration's context. All search/fetch/evaluate calls go through a `ToolRegistry` whose telemetry is included in reflection prompts. If an iteration processes no new URLs the loop stops (stall detection). Maintains a `seen_urls` cache (`data/cache.json`) across runs. Writes `results.json`, `results.csv`, and a plain-text `results.txt` (one URL per line) at the end of every run.
- **`agent_memory.py`** (`AgentMemory`) — persistent cross-run memory (`data/memory.json`): per-query stats (uses, URLs found, new URLs, accepted/rejected), per-domain accept/reject counts, and recent reflection assessments (capped at 10). `summary_for_prompt()` produces the compact dict injected into planning/query-generation contexts; `ineffective_queries()` (used but never yielded a new URL) drives query skipping.
- **`tools.py`** (`ToolRegistry`) — named tool wrappers with call/error counts and last-error capture; exceptions propagate to the orchestrator's existing per-URL error handling.
- **`page_signals.py`** — pure-function page/preference signals shared by the orchestrator and the eval harness: `find_stale_marker()` (EN/DE closed/expired/filled phrases; the orchestrator skips such pages before spending an LLM call), `mentions_location()`/`location_terms()` (preference locations expanded with local-language aliases like München/Deutschland, plus remote markers when preferences ask for remote), and `country_code_for()` (ISO code for Brave's `country` parameter, derived from preference locations).
- **`language.py`** — pure-function posting-language signals: `normalize_language()` (user-entered names/aliases like "Deutsch"/"EN" → canonical lowercase English names; "no preference"-style answers → ""), `detect_language()` (stopword-count detection of the language a user's documents are written in, for the default when no preference is stated), and `language_code_for()` (ISO 639-1 code for Brave's `search_lang` parameter).
- **`url_heuristics.py`** — pure-function URL classifier: `classify_url()` returns `POSTING` (ATS hosts like greenhouse/lever/workday/personio, or job-ID-shaped paths), `LISTING` (generic careers/jobs page), `INDEX` (aggregator search/list pages: Glassdoor `SRCH`, Stepstone `/jobs/<term>`, Indeed/LinkedIn search, or search-style query params), or `OTHER`. `is_aggregator_url()` flags known job-board hosts. The orchestrator's `_triage_urls()` and `_harvest_posting_links()` use these to prioritize employer-hosted postings and down-rank or drop aggregator pages.
- **`notifier.py`** (`TelegramNotifier`) — sends the run's newly accepted jobs (title, score, URL) to a Telegram chat via the Bot API, packing entries into as few messages as fit the 4096-char limit. Constructed in `src/main.py` only when both `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` are set in `.env` and `telegram = true` in `[tool.job_crawler.notify]` (the default). The orchestrator calls `notify_results()` after writing results; notifier failures are logged, never fatal, and empty runs send nothing. `scripts/telegram_setup.py <bot_token>` is a one-shot helper that verifies the token, discovers the chat ID from the user's first message to the bot, writes both into `.env`, and sends a test message.
- **`dashboard.py`** (`DashboardServer`) — read-only monitoring web UI (stdlib `http.server`, no new dependencies): a single embedded HTML page plus JSON APIs (`/api/overview`, `/api/results`, `/api/logs`, `/api/memory`) that aggregate what's already on disk — accepted jobs across the CLI output and every bot user, per-user intake state/scan recency, a live log tail (`data/logs/`, traversal-safe: only files listed in the log dir are served), and per-query/domain agent memory. Pure collector functions (`collect_results`/`collect_users`/`collect_memory`/`collect_overview`/`tail_log`) are unit-testable without a server. Runs standalone (`python -m src.dashboard`) or auto-starts as a daemon thread inside `BotService.run()` (which injects a `status_provider` so the page shows uptime and queued/running scans). Config in `[tool.job_crawler.dashboard]` (`enabled`/`host`/`port`, default loopback:8765 — **no auth, never bind publicly**); `JOB_CRAWLER_DASHBOARD_HOST`/`JOB_CRAWLER_DASHBOARD_PORT` override per-deployment (docker-compose sets host `0.0.0.0` inside the container but maps the port to `127.0.0.1` on the host; see `docs/HOSTING.md` for the SSH-tunnel access pattern).
- **`models.py`** — Pydantic schemas (`SearchQueries`, `SearchPlan`, `Reflection`, `JobEvaluation`, `JobResult`, `IntakeExtraction`) that constrain LLM output and the final result records. `SearchPlan` includes `target_companies` (real employers the plan suggests checking directly). `SearchPlan`/`Reflection`/`IntakeExtraction` fields all default, so partial LLM JSON still validates.

### Telegram bot service (multi-user)

- **`bot_service.py`** (`BotService`, entrypoint `python -m src.bot_service`) — the always-on service. Main thread long-polls `getUpdates` (offset persisted in `data/bot_offset.json` so restarts don't replay messages); a scheduler thread enqueues every ACTIVE user once per day, the first time local wall-clock time in `scan_timezone` passes `scan_hour` and the user's `last_scan_at` predates that moment (so scans land each morning rather than drifting around the clock); a single scan-worker thread runs crawls sequentially (one `Orchestrator.run` at a time keeps Brave/LLM rate limits sane). Each scan builds a fresh `EffortBudget` + `LLMService`/`CrawlerEngine`/`TelegramNotifier` (notifier targeted at that user's chat) with per-user paths from `UserStore.crawl_paths()`. `/run` triggers an immediate scan (deduped against queued/running) and counts as that day's scan. `last_scan_at` is written *before* the crawl so a crashing scan isn't re-enqueued every minute. Config lives in `[tool.job_crawler.bot]` (`poll_timeout_seconds`, `scan_hour`, `scan_timezone`, `intake_max_llm_calls`; `scan_hour`/`scan_timezone` overridable per-deployment via `JOB_CRAWLER_SCAN_HOUR`/`JOB_CRAWLER_SCAN_TIMEZONE`).
- **`intake.py`** (`IntakeManager`) — pure conversation state machine (fully unit-testable; telegram client only used for downloads): `new → awaiting_cv → awaiting_motivation → awaiting_job_prefs → awaiting_answer* → active`. Accepts document uploads or pasted text (`MIN_PASTED_DOC_CHARS`), supports `/skip` for optional steps, `/status`, `/reset`, `/help`. After the documents are in, calls the injected `extract` callable (LLM `extract_search_profile`); missing essentials always produce deterministic fallback questions (`QUESTION_LOCATIONS`, `QUESTION_ROLES`, `QUESTION_LANGUAGE`) even if the LLM asks nothing (the intake prompt only sets `language` when the user explicitly stated one, so the language question is normally asked), answers are fed back into a re-extraction, `/skip` answers a pending question with "no preference", and if the LLM fails entirely `_fallback_extraction` builds preferences straight from the raw answers. Question rounds are capped by `MAX_ANSWERED_QUESTIONS`. Finalization writes a preferences dict in the same shape as `preferences.json` (`location`, `locations`, `job_titles`, `job_description_keywords`, `industries`, `language` — the latter defaulting to `language.detect_language` over the user's own documents/answers when no preference was given).
- **`user_store.py`** (`UserStore`, `UserRecord`) — per-user persistence under `data/users/<chat_id>/` (chat id sanitized against path traversal): `record.json` (state, preferences, pending questions, answers, `last_scan_at`), extracted document texts (`cv.txt`, `motivation.txt`, `job_description.txt`), and that user's isolated crawl state (`cache.json`, `memory.json`, `results.*`). `reset()` restarts intake but keeps crawl cache/memory.
- **`telegram_api.py`** (`TelegramClient`, `parse_update`) — thin requests-based Bot API wrapper: long-poll `get_updates`, `send_message` (splits >4096 chars), `download_document` (via `getFile`, capped at 15MB). `parse_update` normalizes raw updates into `IncomingMessage`/`IncomingDocument`.
- **`document_text.py`** — `extract_text(bytes, file_name, mime)` for PDF (`pypdf`), DOCX (`python-docx`), and plain text; raises `DocumentExtractionError` with a user-facing message for scanned PDFs, legacy `.doc`, or <40-char extractions.
- **`Dockerfile` / `docker-compose.yml`** — python:3.11-slim + uv + Google Chrome (for the botasaurus browser fallback; amd64 only), `CMD python -m src.bot_service`, `restart: unless-stopped`, `./data` volume, `shm_size: 1gb`, secrets via `env_file: .env`.

Agent behavior toggles live in `[tool.job_crawler.agent]` (`enable_planning`, `enable_reflection`, `ats_query_boost`, `company_query_boost`, `exclude_aggregator_sites`, all default true; with reflection disabled the heuristic fallback is still used) and `memory_path` in `[tool.job_crawler.output]`. `ats_query_boost` makes the orchestrator prepend up to 2 deterministic `site:`-targeted queries per iteration (built from plan roles × `ATS_QUERY_SITES`, rotating via the already-searched set) so Brave surfaces individual postings instead of board indexes; `company_query_boost` similarly prepends 1 `"<company>" careers <role>` query per iteration rotating through the plan's `target_companies`. The query-generation prompt also asks the LLM for such queries, but injection doesn't rely on the model complying. `exclude_aggregator_sites` drops aggregator index pages at triage (Brave ignores `-site:` in queries), and `max_harvest_links` in `[tool.job_crawler.search]` caps how many posting links are harvested per careers/board page. `freshness` in `[tool.job_crawler.search]` (default `"pm"`, empty string disables) passes Brave's freshness filter so only recently indexed pages are returned — but not for `site:` queries, whose narrow result sets it starves (dead ATS postings are caught at fetch time instead: they don't 404 but silently 302 to the company's board page, which `page_signals.redirected_off_posting()` detects in `CrawlerEngine.fetch_page` by comparing the requested URL with the response's final URL).

### Integration eval (`evals/`)

`evals/run_eval.py` is the feedback loop for result quality: it runs the *real* agent (Brave + OpenRouter, keys from `.env`) once per search profile in `evals/profiles.py` (6 profiles varying role, location, and industry: Berlin ML engineer, Berlin project manager, Munich frontend, Amsterdam data engineer, remote-Germany backend, Berlin food-industry product manager), each in an isolated `evals/runs/<tag>/<profile>/` dir (fresh cache/memory, browser fallback off so runs are comparable). Every accepted result URL is then independently refetched by `evals/checks.py` and scored on the known failure modes plus posting shape: `live` (resolves with content), `fresh` (no `page_signals` stale marker), `location_ok` (`mentions_location` against the profile), `domain_ok` (`mentions_domain` against the profile's `industries`; `None` when the profile states none), `posting` (`classify_url == POSTING`). Per-profile `scorecard.json` and a combined `report.json`/`report.md` land in `evals/runs/<tag>/`; compare tags (e.g. `baseline` vs a fix) to measure improvements. `tests/test_integration_eval.py` wraps the same loop as an opt-in pytest (`RUN_INTEGRATION_EVAL=1`, one profile; `=all` for all profiles) asserting minimum fresh/location rates.

### Mock mode

`src/mock_runner.py` provides `MockLLM`/`MockCrawler` fakes (fixed responses from `tests/mock_data.py`) wired through the *same* `Orchestrator` used in production, exercising the real control flow (plan, query generation, evaluation, reflection) without network calls. `run_mock_test.py` runs this loop and asserts exact call counts — useful as a fast sanity check and it's what CI runs after `pytest`. The unit tests in `tests/test_agent_loop.py` use richer `ScriptedLLM`/`ScriptedCrawler` fakes to pin down loop behavior (plan/reflection propagation into contexts, memory-driven query skipping, stall detection, budget/max-results stops).

## Conventions

- All modules use `from __future__ import annotations` and dataclass/Pydantic models for structured data.
- Config is threaded explicitly through constructors (no globals/singletons) — `Config` and `EffortBudget` are passed into `LLMService`, `CrawlerEngine`, and `Orchestrator` alike, which is what makes swapping in mocks straightforward.
- Failures inside the orchestrator's per-URL loop (fetch/score errors) are caught, logged, and the URL is added to `seen_urls` so a bad URL doesn't get retried on the next run.
